## Headline finding: `Identifier` timestamp/counter packing (Major)

This is the one finding from this batch with real blast radius — `Identifier` is the ID generator for the entire persisted data model (36 entity prefixes, 41 SQL migrations depend on IDs sorting correctly). I'm **not** silently patching the encoding, because the fix has a backward-compatibility decision the review can't make unilaterally:

- **Option A — widen the packed field to 7 bytes (56 bits).** Fixes both the `timestamp()` truncation and the ~2.18-year wrap (56 bits ÷ 4096 counter-steps ≈ 557 years of headroom). Changes `LENGTH - 12` → `LENGTH - 14` for the random suffix, i.e. **the ID format itself changes** (one more hex char, two fewer random chars). Any already-persisted ID (format version implied by `CACHE_VERSION`-independent, this isn't cache-versioned) stays parseable for reads since `timestamp()` just slices differently *if* you can tell old-format from new-format IDs apart — but nothing in the current ID string distinguishes format versions, so a mixed old/new ID database would have `timestamp()` silently miscompute for every pre-fix ID.
- **Option B — keep 6 bytes, drop the `× 4096` multiplication, cap `counter` to fit in far fewer bits (e.g. pack `timestamp_ms` directly in the available bits and use a smaller counter window, matching how ULID actually does it: 48 bits raw timestamp, counter stored in the *random* suffix region instead of multiplied into the timestamp).** Avoids changing total ID length, but still changes the encoding — same old/new-ID ambiguity problem as Option A, and reordering requires more surgery since monotonicity currently depends on the counter being inside the sortable timestamp field.
- **Option C — leave the 48-bit field as-is but stop claiming monotonic ordering beyond ~2.18 years, and fix only `Identifier.timestamp()`'s correctness by changing what it reconstructs (document it as "ms-since-last-cache-epoch" rather than true Unix ms).** Smallest change, but doesn't actually fix the underlying sort-order wraparound — just stops pretending the derived timestamp means something it doesn't. Not a real fix, listed only as the "do nothing functionally, fix the lie" baseline.

**Flagging as a question, not guessing:** given 41 existing migrations and presumably live/seeded data using the current 6-byte/48-bit format, which of these (or some versioned-ID-format migration path) is intended? This determines whether the fix is a clean isolated patch or needs a data-migration companion. Proceeding to the next batch; will hold this specific fix for your decision rather than pushing a guess into something that re-keys every table's sort order.
